## What I'd keep exactly as-is

- **Rejecting A was right, and for the right reason.** CORS, forbidden headers, and opaque responses make a browser-only general HTTP client impossible, not just inconvenient. Your comparison table captures this correctly.
- **Rejecting C was also right.** Leases, claim races, crash recovery of queued secrets, and ambiguous remote effects are enormous costs for requirements you don't have. B's synchronous model with a bounded 30s cap is the smallest complete solution.
- **Collections as bounded aggregates with ****`expectedRevision`**** atomic replaces** is the correct MongoDB pattern for your operations (reorder, move, duplicate all become single-document writes with 409 semantics).
- **Immutable history snapshots separated from editable definitions**, with replay re-resolving against current context rather than trusting stored secrets.
- **The exact-match local demo exception** (not suffix matching — avoids `localhost.evil.com`-style bypasses) and routing the demo through real loopback HTTP instead of short-circuiting to fixtures. That last point keeps your tested execution path honest.
- The compiler/policy/transport/normalizer seams are ideal for your stated meta-goal of injectable, diagnosable defects later.

## Gaps I'd fix before implementation

**1. Your DNS pinning strategy may not survive contact with Bun.** The clean Node pattern — a custom `lookup` function passed to `http.request` — depends on Bun's `net` compatibility, and custom `lookup` support has historically been a gap. Since your entire SSRF defense hinges on this, define the fallback now: resolve via `dns.promises.lookup(host, { all: true })`, policy-check *every* returned address, then connect by IP with `servername` set to the real hostname (and an explicit `Host` header for plain HTTP), verifying certificate identity against the hostname, not the IP. Also make sure the blocklist covers the sneaky cases: IPv4-mapped IPv6 (`::ffff:127.0.0.1`), 6to4/NAT64 embedded ranges, `0.0.0.0`, IP-literal URLs (skip DNS but still policy-check), and cloud metadata addresses. Validating only A records while AAAA records sail through is a classic hole.

**2. Nothing transitions orphaned ****`running`**** records to ****`interrupted`****.** You define the `interrupted` outcome but never assign responsibility for the transition. This isn't theoretical: your own runtime contract says backend-only restart preserves data, and the reference uses `bun --watch` — every file save during development wipes the in-memory registry while `running` history rows persist. Add a boot-time sweep that marks orphaned running records as `interrupted`, and define cancel semantics when the registry misses but history exists (post-restart, the cancel endpoint should read history state, not 404).

**3. Reconsider ****`Accept-Encoding: identity`****.** Servers are allowed to ignore it, and CDNs with force-compression configs frequently do. Your local demo targets are under your control, so this flaw will be invisible in your own testing — but your completion evidence says "reaches a real HTTP endpoint," and a reviewer hitting a real public API behind a CDN will get an unusable base64 blob. `node:zlib` is available in Bun and decompressing gzip/deflate/br is \~15 lines on your existing capture stream. Keep the truthful wire-byte accounting (`receivedBodyBytes` stays as-is, add decoded size) and the truncation logic; this is high-ROI for a "polished" client.

- **The 30s synchronous hold through the read-only Vite proxy.** `http-proxy` defaults to no timeout, so dev is probably fine, but Bun's handling of Node's `server.requestTimeout`/`headersTimeout` options is unverified. - **Idempotency wording is ambiguous as written.** "A completed duplicate with the same input fingerprint returns the stored result" could be read as: a fresh Send with unchanged input gets a cached response. Make explicit that retry-safety is keyed by `executionId` (network retry protection), the fingerprint only detects ID reuse with different inputs, and every new Send performs a new target call — that's the Postman-like expectation.
- **History persistence sizing.** 1 MiB capture → \~1.4 MiB base64 per entry × 200 retained ≈ 280 MB worst case per profile. Each document is fine under the 16 MB limit, but consider capping the *persisted* body (e.g., 256 KiB) below the capture limit, with the full body only in the live response.

Executive Summary: "Request Desk" (Postman Clone)

Objective: Build a robust, secure, full-stack HTTP client for developers and assessment evaluation.

Stack: React 19 (Vite) + Express 5 (Bun runtime) + MongoDB 8+ (Mongoose) + Zod validation.

Selected Pattern: Architecture B — Synchronous Server-Side Execution.

1\. Why Architecture B Won

Architecture	Execution Model	Verdict	Reason

A: Browser Client	Direct fetch() from React	Rejected	Crippled by browser CORS, forbidden headers, and security risks with client-side secrets.

B: Synchronous Server	Express executes target HTTP calls synchronously	Selected	Full HTTP fidelity, rock-solid SSRF protection, clean state boundaries, and zero extra infrastructure needed.

C: Async Queue / Poller	Express queues jobs in DB; background worker polls	Rejected	Overkill for interactive developer requests; adds lease locks, polling lag, and crash recovery complexity.

2\. The 6 Core Capabilities

Request Builder & Execution: Supports GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS; parameterized URL/query/headers; raw, JSON, and URL-encoded bodies; send/cancel/timeout controls.

Collections: Bounded hierarchical aggregates (1-level folder nesting); atomic reordering; duplicate and delete support.

Environments: Key-value stores supporting both plain variables ({{base\_url}}) and server-secret references (local\_token); collection defaults with active environment overrides.

Target Authentication: Inherit, Bearer, Basic, and API Key (header/query); strict validation blocks duplicate explicit headers before sending.

Response Viewer: Accurate server-measured timing (TTFB + total), raw headers, byte counts, collapsible/searchable JSON tree, and escaped HTML/XML rendering.

Execution History: Immutable audit trail of every accepted send; captures exact request/response snapshots; supports reopening as an editable draft or direct resending.

3\. Core Architectural & Security Rules

SSRF Defense: Public IPv4/IPv6 addresses only. All targets resolve DNS before socket connection; non-public/private ranges are rejected; sockets connect strictly to the pinned validated IP.

No Auto-Redirects: 3xx responses are returned as inspectable data to avoid leaking credentials across hostnames.

Secrets Separation: Real secrets are never saved to MongoDB. Environments only persist an alias that maps to server-side configuration.

Isolated MongoDB Aggregates: Collections store folders and requests inside a single bounded document (capped at 2 MiB) with an incrementing revision number. This allows atomic updates on standard standalone MongoDB without replica-set transactions.

Self-Contained Demo Suite: A local /demo/v1 loopback API is seeded into the database, allowing fully functional evaluation with zero outbound internet access.

4\. Key Recommendations & Action Items for Implementation

While the specification is exceptionally solid, incorporate these 7 targeted refinements during implementation:

1\. Prevent Multi-Tab Revision Collisions (Critical)

Problem: Because an entire collection is one aggregate document with a single revision, editing Request A in Tab 1 and saving it will bump the revision. When the user tries to save Request B in Tab 2, it will trigger an unnecessary 409 REVISION\_CONFLICT.

Fix: Update individual requests using MongoDB positional operators ($set: { "requests.$": ... }), and limit collection-wide revision checks to structural operations (rename collection, reorder/delete folders).

2\. Concrete DNS Pinning in Bun/Node

Problem: Connecting to an IP address directly over HTTPS breaks TLS certificate verification and SNI checks.

Fix: Implement a custom lookup function inside https.Agent. The agent resolves and verifies the safe public IP, while Node/Bun retains the original hostname for SNI and certificate validation.

3\. Handle Browser Disconnects Gracefully

Problem: If a user closes the browser or tab mid-flight, the frontend cannot call the /cancel endpoint.

Fix: Listen to req.on('close') on the incoming Express request. If !res.writableEnded, trigger server-side cancellation immediately to avoid burning socket slots.

4\. Clarify JSON Variable Interpolation

Problem: Literal string substitution of variables containing newlines or unescaped quotes inside JSON bodies will cause JSON parsing errors.

Fix: Document clearly that substitution is literal, or provide a UI helper that prompts the user on how strings with quotes/newlines should be formatted.

5\. Add a "Follow Redirect" Action for 3xx Responses

Problem: Disabling automatic redirects protects against SSRF, but trailing-slash redirects (301 / 308) will be common.

Fix: When a 3xx response has a Location header, show a one-click button in the response UI: "Open Location in new tab".

6\. Dynamic Demo Port Binding

Problem: Hardcoding [http://127.0.0.1:8000/demo/v1/](http://127.0.0.1:8000/demo/v1/) will break the local demo suite if the app is run on a different port (e.g., PORT=8080).

Fix: Dynamically construct the loopback exception origin from the runtime configuration (http\://127.0.0.1:${config.PORT}/demo/v1/).

7\. Limit DOM Node Budget for Response Tree

Problem: Rendering a custom React recursive tree for a 1 MiB JSON file (\~50,000 lines) will freeze the browser without virtualization.

Fix: Default tree expansion to level 1, cap interactive tree rendering at 2,000 nodes, and automatically fall back to the raw \<pre> view with a clear performance notice if the payload exceeds that budget.

- **Simplify secrets initially:** support ordinary variables first, keep server-side secret aliases tightly limited, and avoid arbitrary secret creation in v1.

- **Formalize execution properly:** clearly define admission, running, completion, cancellation, timeout, network failure, interrupted state, and persistence failure.
- **Use one canonical execution state machine** and keep database persistence status separate from HTTP execution outcome.
- **Track cancellation uncertainty:** distinguish requests cancelled before dispatch from ones that may already have caused remote side effects.

- **Make SSRF/public-target rules explicit and testable:** localhost, `.local`, mixed private/public DNS, IPv4-mapped IPv6, TLS hostname validation, ports, etc.
- **MongoDB should be authoritative for preferences;** local storage should only help first paint.
- Clarify missing contracts around **JWT/session storage, CSRF, URL snapshots, header casing, history deletion races, safe DB reset, and offline/local acceptance testing**.

A lot of the design is good but potentially over-engineered for the assessment: deep SSRF protection, response-body secret redaction, HMAC execution fingerprints, raw binary fidelity, detailed timings, crash recovery, multiple profiles, and auth inheritance should mostly be **hardening rather than initial implementation**.

The document should also add:

- a **Non-Goals / Deferred Hardening** section,
- a clear **Core → Acceptance → Hardening** roadmap,
- and explicit invariants such as:
  - Send never mutates a saved request.
  - Every execution gets exactly one terminal outcome.
  - History becomes immutable after completion.
  - Target 4xx/5xx responses are still valid HTTP results.
  - Credentials/JWTs are never leaked to the target.
  - Collection changes are revision-checked.
  - History is always profile-scoped.
  - UI results must come from real HTTP execution, not fixtures.
